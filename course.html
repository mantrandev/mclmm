CLI sống ở đâu?

Khi gõ git, mclmm, hay node — shell tìm chúng ở đâu? Câu trả lời là $PATH. Hiểu $PATH là hiểu toàn bộ câu chuyện.

Máy tính không "biết" mọi lệnh. Khi gõ một lệnh, shell (zsh/bash) sẽ tìm kiếm một file executable có tên đó trong danh sách thư mục được định nghĩa sẵn — danh sách đó là $PATH.

Bạn gõ: mclmm scan
Shell duyệt qua từng thư mục trong $PATH:
/usr/local/bin → tìm thấy "mclmm" → chạy nó
/usr/bin → (bỏ qua vì đã tìm thấy rồi)

Nếu không tìm thấy ở đâu, shell trả về: 

command not found: mclmm

$PATH hoạt động thế nào?

$PATH là một biến môi trường — một chuỗi các thư mục ngăn cách bởi dấu :. 

echo $PATH
# /usr/local/bin:/usr/bin:/bin:/usr/sbin:/sbin

Shell duyệt từ trái sang phải, dừng lại ở thư mục đầu tiên tìm thấy file.

/usr/local/bin → /usr/bin → /bin → /usr/sbin → /sbin
Tìm trái → phải. Dừng khi gặp match đầu tiên.

Xem $PATH của bạn

# In từng thư mục trên một dòng — dễ đọc hơn
echo $PATH | tr ':' '\n'

Thêm thư mục vào $PATH

# Thêm vào ~/.zshrc
export PATH="$HOME/my-tools:$PATH"

# Reload shell
source ~/.zshrc
Tip /usr/local/bin là nơi "chuẩn" để cài tool do người dùng tự quản lý trên macOS. Homebrew cũng cài vào đây. Luôn có trong $PATH mặc định.

Symlink — ln -s

Symlink (symbolic link) là một file đặc biệt — nó không chứa data, chỉ trỏ đến một file khác. Giống như shortcut trên Windows, nhưng mạnh hơn nhiều.

Cú pháp

ln -s <file_gốc> <tên_link>

# Ví dụ thực tế:
ln -s /Users/maybe/Desktop/projects/mclmm-cli/mclmm /usr/local/bin/mclmm
/usr/local/bin/mclmm ──symlink──→ /projects/mclmm-cli/mclmm
Link chỉ tốn ~200 bytes. File thật không bị copy, không bị move.

Kiểm tra symlink

ls -la /usr/local/bin/mclmm
# lrwxr-xr-x  1 root  /usr/local/bin/mclmm -> /projects/mclmm-cli/mclmm

readlink /usr/local/bin/mclmm
# /projects/mclmm-cli/mclmm

Xóa symlink

rm /usr/local/bin/mclmm   # chỉ xóa link, file gốc vẫn còn

Ưu điểm của symlink

ĐiềuGiải thích
Edit file gốc = thay đổi ngayLink trỏ trực tiếp — không cần reinstall
Không copy fileTiết kiệm disk, luôn dùng version mới nhất
Dễ gỡChỉ rm link, file gốc nguyên vẹn
Shell-agnosticBash, zsh, fish, bất kỳ shell nào đều gọi được
Script-agnosticTool không cần là zsh — Python, Ruby, Go đều ok
Lưu ý Luôn dùng đường dẫn tuyệt đối khi tạo symlink. Đường dẫn tương đối sẽ hỏng khi bạn cd sang thư mục khác.

Shell Source — inject vào zsh

Cách thứ hai là "nhúng" code vào shell session. Khi terminal khởi động, nó đọc file ~/.zshrc và chạy mọi thứ trong đó.

3 kiểu inject vào zsh

# ~/.zshrc

# Kiểu 1: Alias — gán tên cho một lệnh dài
alias mclmm="zsh /path/to/mclmm"

# Kiểu 2: Function — code thật sự chạy trong shell hiện tại
mclmm() {
  # function body chạy trong shell process hiện tại
  echo "hello from mclmm"
}

# Kiểu 3: Export PATH — thêm thư mục vào PATH
export PATH="$HOME/my-tools:$PATH"

Source là gì?

source ~/.zshrc
# hoặc viết tắt:
. ~/.zshrc

source đọc và thực thi file trong shell hiện tại — không spawn process con. Đó là lý do function/alias trong ~/.zshrc có thể ảnh hưởng đến shell của bạn (thay đổi biến, cd vào thư mục, v.v.).

Ví dụ thực tế: fzf, z, nvm

# ~/.zshrc — cách fzf, nvm inject vào shell

# fzf: cần hook vào keybindings của zsh
[ -f ~/.fzf.zsh ] && source ~/.fzf.zsh

# nvm: cần thay đổi PATH và nhiều biến môi trường
export NVM_DIR="$HOME/.nvm"
[ -s "$NVM_DIR/nvm.sh" ] && \. "$NVM_DIR/nvm.sh"

# z (jump): cần hook vào PROMPT_COMMAND để track history
source /usr/local/etc/profile.d/z.sh
Tại sao nvm PHẢI source, không thể dùng ln? Vì nvm use 18 phải thay đổi $PATH của shell đang chạy. Một process con (binary/symlink) không thể sửa biến môi trường của process cha.

So sánh trực tiếp

Symlink (ln -s)

  • File executable nằm trên $PATH
  • Shell spawn process con để chạy
  • Không cần khởi động lại terminal
  • Hoạt động với mọi shell
  • Edit file gốc → có hiệu lực ngay
  • Không load overhead khi mở terminal
  • Không thể sửa env của shell cha

Shell Source (~/.zshrc)

  • Code chạy trong shell hiện tại
  • Có thể sửa $PATH, biến, alias
  • Cần source ~/.zshrc sau khi sửa
  • Chỉ hoạt động với shell đó (zsh)
  • Có thể làm chậm startup terminal
  • Phù hợp: alias, function, plugin
  • Bắt buộc khi cần hook vào shell

Khi nào dùng cái nào?

Tình huống Dùng gì Lý do
CLI tool độc lập (git, mclmm, ffmpeg) Symlink Không cần hook vào shell
Cần thay đổi $PATH runtime (nvm, pyenv) Source Phải sửa env của shell cha
Alias ngắn (ll, gst, gco) Source / alias Chỉ là tên gọi khác, không phải program
Plugin zsh (fzf keybinding, autocomplete) Source Cần hook vào zle (zsh line editor)
Script Python/Ruby/Go Symlink Shebang lo phần còn lại
Cần cd vào thư mục (z, autojump) Source / function Process con không thể cd shell cha
Quy tắc đơn giản Nếu tool cần sửa environment của shell đang chạy → source. Còn không → symlink.

Shebang — dòng ma thuật đầu file

Khi bạn chạy một file executable, kernel (macOS) đọc 2 byte đầu tiên. Nếu là #! — đó là shebang, kernel sẽ dùng interpreter được chỉ định để chạy file. 

#!/usr/bin/env zsh       # dùng zsh tìm được trong PATH
#!/usr/bin/env python3   # dùng python3
#!/usr/bin/env node      # dùng node
#!/bin/bash              # dùng bash tại đường dẫn cố định

Tại sao dùng /usr/bin/env?

# Cách cứng — hỏng nếu zsh không ở /bin/zsh
#!/bin/zsh

# Cách linh hoạt — tìm zsh trong $PATH của user
#!/usr/bin/env zsh

Dùng /usr/bin/env để script hoạt động dù interpreter được cài bởi Homebrew hay ở vị trí khác nhau trên các máy khác nhau.

Flow khi chạy mclmm

1. Bạn gõ mclmm scan
2. zsh tìm trong $PATH → thấy /usr/local/bin/mclmm
3. Đó là symlink → follow đến /projects/mclmm-cli/mclmm
4. Kernel đọc dòng đầu: #!/usr/bin/env zsh
5. Kernel spawn zsh với argument là file đó
6. zsh chạy mclmm scan như một script

Chmod — file phải executable

# Xem permission hiện tại
ls -la mclmm
# -rw-r--r--  → chưa executable (không có x)
# -rwxr-xr-x  → executable (có x)

# Cấp quyền execute
chmod +x mclmm

# Đọc permission: r=read, w=write, x=execute
# rwxr-xr-x = owner:rwx, group:r-x, others:r-x
Symlink mà file gốc không có +x → sẽ lỗi Permission kiểm tra trên file gốc, không phải link.
Chương 7

mclmm — thực tế

Áp dụng tất cả các khái niệm trên vào mclmm.

Tại sao mclmm dùng symlink?

#!/usr/bin/env zsh    ← shebang: chạy như process độc lập
emulate -L zsh       ← reset zsh options, không phụ thuộc ~/.zshrc
setopt local_options null_glob

mclmm không cần sửa $PATH, không cần hook vào shell, không cần biến môi trường từ shell cha. Nó là một tool độc lập — symlink là cách đúng.

Dev workflow với symlink

# Cài một lần
ln -s "$PWD/mclmm" /usr/local/bin/mclmm

# Edit file gốc trong editor
# → Không cần reinstall
# → Gõ mclmm ngay lập tức thấy thay đổi

# Xem symlink trỏ về đâu
readlink /usr/local/bin/mclmm

Prefixed commands

# Cùng một file, nhiều tên khác nhau
for s in storage scan cache xcode uninstall clean; do
  ln -s "$PWD/mclmm" "/usr/local/bin/mclmm-$s"
done

# Bây giờ cả hai đều hoạt động:
mclmm scan
mclmm-scan

Script đọc $0 (argv[0]) để biết nó được gọi bằng tên gì, từ đó tự dispatch sang subcommand tương ứng. Đây chính xác là cách git hoạt động: git-commit, git-push v.v. đều là symlink về cùng một binary.

So sánh nếu mclmm dùng source thay vì ln

Dùng ln (hiện tại — đúng)

  • Edit script → có hiệu lực ngay
  • Terminal mở nhanh, không load thêm
  • Chạy được từ bash, fish, script khác
  • Không ảnh hưởng ~/.zshrc
  • Dễ gỡ: rm /usr/local/bin/mclmm

Dùng source (sai cách)

  • Phải source ~/.zshrc sau mỗi lần edit
  • Làm chậm startup terminal
  • Chỉ chạy được trong zsh session
  • Có thể xung đột với alias khác
  • Gỡ cài đặt: phải sửa ~/.zshrc thủ công
